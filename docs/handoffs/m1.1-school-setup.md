# Handoff → Frontend: M1.1 part 1 — School setup (E2.1–E2.3, E4.2)

> Backend status as of 2026-10-13. Contract: `contracts/openapi.json` (run `npm run api:types`). Parts 2 (staff) and 3 (students & guardians) follow in their own handoffs.

## What exists now
Admins can manage sessions and terms (with one current term), classes (year group + arm, capacity, form teacher), the subject catalogue, and which subjects each class offers and who teaches them. All staff can read the lists; parents and students can't (they only get the current term). Every change is audited automatically.

Dates are `YYYY-MM-DD`. `TermDto.name` is ready to display ("First Term 2026/2027").

## Rules the UI should mirror (the server enforces them anyway)
- Session name is two consecutive years `YYYY/YYYY`; it ends after it starts. A session can't be shrunk so that its terms fall outside it.
- Terms: one of each number per session, in order (First before Second before Third), inside the session dates, not overlapping. A mid-term break needs both dates and must fall inside the term.
- Class arm is required (≤ 32 chars). Capacity is 1–200 and can't go below the number of active students already in the class.
- Subject code: letters and digits only, ≤ 10. Name ≤ 100. Name and code are unique (case-insensitive).
- Inactive subjects stay on classes that already offer them but can't be newly added.
- A subject with scores entered in a class can't be removed from that class (422; show `detail`, which names the subjects).
- Field errors come back as 400 `validation` with `errors` keyed by field: `name`, `startsOn`, `endsOn`, `number`, `midTermStartsOn`, `midTermEndsOn`, `arm`, `capacity`, `classLevelId`, `formTeacherId`, `code`, `subjects`.
